Research brief · passive UI mirroring for Unity games

Semantic UI offloading: what we built, what it proves, and what it does not

We built a system that watches a running Unity game, describes its user interface as data instead of pixels, and redraws that interface in a separate, generic client — live, and again later from a recording. We tested it on three real student games.

Evidence: three games, one shared implementation (v1), final measured sessions final-03. Every number below is read from recorded session data.

The idea in one paragraph

A cloud-gaming service today sends the player a video of the whole screen, including the menus, buttons and text. Those UI elements are highly structured: a button is a rectangle with an image, a label and a state. Our hypothesis is that the UI can be sent as meaning — "a button named Start, here, with this image, currently enabled" — and redrawn on the client. That could make UI sharper, cheaper to transmit, and accessible to local tools. This project asks the prerequisite question: can we capture a real game's UI completely and faithfully enough, without modifying how the game behaves?

Core claim. Static analysis tells us what UI assets and templates exist. A passive runtime sniffer tells us what the UI actually is at this moment. A generic client redraws that state — but it is not the game's renderer, so it can be geometrically exact while still looking different.

What static analysis can and cannot tell us

Static analysis means inspecting the game's files without running it. It is useful, but it cannot, on its own, produce the UI a player actually sees.

Static analysis can findOnly runtime can know
Which UI templates exist (a "shop row", a "pause menu")How many shop rows were created, and in what order
Which images, fonts and materials are referencedThe current score, player name, language, health
The layout rules authored in the editorFinal positions after animation, layout and screen scaling
Which scripts could show or hide thingsWhich elements are visible right now
Scroll views and lists as componentsThe current scroll position and what is clipped

A concrete example: static analysis sees a shop-row template and the code that loops over server data to create rows. It cannot know how many rows the server will send or what each says. It gives a superset of building blocks, not the concrete state. Computing every reachable UI state of an arbitrary program is, in general, undecidable.

So in our system, static analysis has a narrow job: an editor-time pass builds an asset identity index, so a sprite seen at runtime can be named by its stable project ID rather than a per-run memory address. Measured: 207 of 215 referenced assets in Unchained resolved to stable IDs; the rest are explicitly labelled session-local.

Why we do not simply copy the game's scenes and prefabs into the client: a prefab drags in scripts, shaders, animation controllers and packages. Making it render correctly means copying the whole dependency chain, and the client would start running game code — at which point it is a second copy of the game, not a passive mirror, and recordings would no longer replay independently.

How the sniffer works

  1. Injected, but passive. A small benchmark module is compiled into a copy of the game. It starts itself at launch and only reads: it never changes a value, clicks a button, creates or destroys game objects, or touches game timing. Network and disk I/O run on background threads so the game's frame loop is never blocked.
  2. Sampled after layout. Unity announces when it is about to draw the UI. At that point all layout is resolved, so the sniffer reads final positions — at most once per sampling interval (15 Hz).
  3. Full snapshot, every time. Each sample is the complete UI tree: every node, its parent and sibling order, visibility, final on-screen rectangle, text, colours, image reference, draw order and clip region. No deltas. A lost message is repaired by the next one, and a replay can start anywhere.
  4. Final screen geometry is the ground truth. The sniffer records where each element ended up on screen, not the authoring rules that produced it. The mirror places elements there directly and never re-runs the game's layout — that is what eliminates a whole class of "the button is in the wrong place" errors.
  5. Images sent once. The first time an image is referenced, its pixels are extracted and sent with a content hash. Later snapshots reference it by ID and version.
  6. Everything unsupported is recorded. Any component or property the generic mirror cannot reproduce generates an explicit record — which node, which property, why, and whether it affects what you see.
  7. The mirror diffs by ID. On each snapshot the mirror creates new nodes, updates existing ones, re-parents moved ones and deletes vanished ones. It never runs game code.

What "completeness" means — three different levels

"Complete" is easy to over-claim. We separate it into three levels and state which ones we can guarantee.

guaranteed · measured

1. Capture completeness

Within each snapshot, every node under every UI root in every loaded scene is emitted — including hidden ones. Measured structural coverage: 100% in all three games.

guaranteed · measured

2. Accounting completeness

Nothing is silently skipped. Every unsupported property, missing image and fallback font is counted in its own denominator and reported.

not guaranteed

3. State coverage

Whether we ever visited every screen the game can show. This depends on the exploration driving the game, and today that is our weakest part.

Level 3 is where static analysis becomes valuable again: its template list can serve as the denominator for exploration. "The game declares 40 UI templates; exploration instantiated 31; these 9 were never seen." That turns an unknowable question into a measurable one. This is proposed, not yet implemented.

If extraction is correct, why is fidelity still imperfect?

Because correct description is not the same as having the original renderer. We send "a button with this image and a glow shader called MapButton". The client has the image and the rectangle, but not the shader program that produces the glow. The geometry is exact; the appearance differs.

A separate category: bugs in the conversion itself. Our visual checkpoints caught six real defects where the data was right but the mirror drew it wrong — an upside-down axis in UI Toolkit, trimmed sprites stretched, font sizes in the wrong units, IDs silently rounded by the JSON parser, a stretch rule ignored, and a mirror that lagged five seconds behind. Every one showed 100% structural coverage while visibly wrong. That is why we insist on paired screenshots, not just node counts.

Distinct states are over-counted. A "fingerprint" changes whenever anything visible moves or its text changes, so frames of a scrolling credits roll or an animation each count as a new state. In Smoke Break 202 of 208 fingerprints appear in a single snapshot; about 6 are real screens. The final automated run did not reach gameplay in Smoke Break — see the auto-explorer section.

How to read this. Geometry, structure, visibility and order are exact everywhere. "Fully reconstructed" is strict — one unsupported property downgrades a node — so Spurpunk's 15.8% reflects a single custom material on most of its buttons, not misplaced buttons. The replay shortfalls are all timing: in live mode an image may not have arrived yet for the first frames that use it.

Bandwidth: honest numbers

The prototype deliberately sends verbose full JSON snapshots, because they are easy to audit. That is expensive. We measured what a production encoding could achieve on the recorded sessions (about 150 samples per game, spread across each session):

For scale, a 1080p game video stream is typically 10–30 Mbit/s. The prototype's raw format is worse than video. The delta estimate is two orders of magnitude better — but it is an offline calculation, excludes one-time image transfer, and has not been implemented or tested live.

The UI auto-explorer — current state and weakness

To collect many UI states, something has to drive the game. Today that is a scripted sequence of clicks at fixed screen positions per game. It is blind: it does not look at the UI before clicking. On Spurpunk, the first script clicked on character artwork and never left the splash screen; we had to inspect screenshots and re-aim it. In the final measured runs, Spurpunk reached its map and Unchained reached in-game dialogue and the pause menu (its title screen and gameplay share one scene). Smoke Break stayed in its main-menu scene: an earlier run did reach gameplay, but a Continue button appeared partway through later sessions and the fixed-position click stopped reaching gameplay (not yet diagnosed).

The sniffer already knows, every frame, which elements are interactive, where they are, and whether they are enabled. The natural next step is a semantic explorer that picks actions from that list, prefers unvisited states, deduplicates states by hash, and measures coverage against the static template list. The accompanying toy demo shows the difference between the two.

Next steps

  1. Semantic explorer driven by the sniffer's interactable list, with coverage measured against the static template superset.
  2. Delta + binary encoding, implemented and measured live against a video-stream baseline.
  3. Pixel-level fidelity metric (e.g. SSIM on UI-only regions) — the current gate proves geometry, not appearance.
  4. Input path back to the game: today the mirror is display-only; offloading needs clicks on the client to reach the game.
  5. Build-time visual extraction: convert shaders, UXML/USS and fonts where licensing allows into a neutral format, without running game code.

Hard questions an advisor should ask — and our answers

Isn't this just screen streaming with extra steps? Why not send pixels?

Pixels are the baseline we want to beat, not an alternative we ignored.

Pixels are opaque: the client cannot re-render text at its own resolution, read labels for accessibility, or respond locally. Sending structure makes those possible. Whether it is also cheaper is an open measurement (see bandwidth). We intentionally did not add video to the mirror, because it would have hidden reconstruction errors.

Your full snapshots are up to 226 Mbit/s. That is far worse than video. How is this "offloading"?

Correct — the prototype format is not the deployment format.

Full JSON was chosen for auditability. On the same recordings, 94–99.9% of nodes do not change between frames; an estimated changed-nodes-only encoding is 0.04–0.18 Mbit/s. That number is an offline estimate, not a live result, and we present it as such.

Geometry error is 0.0000%. Isn't that trivially true, since you copy the rectangle?

Yes, partly — and that is the point of the check.

It does not measure visual similarity. It measures that the pipeline — coordinate conversion, scaling, letterboxing, hierarchy, ordering, clipping — does not distort the captured geometry. That pipeline failed in six ways during development, all invisible to node counts. Appearance is measured separately (render coverage) and needs a pixel metric, which we list as future work.

Render coverage is 15.8% on Spurpunk. So the mirror mostly does not look like the game?

Its buttons are in the right place with the right image, but lack a custom glow shader.

The metric is strict: one unsupported property marks the whole node partial. Spurpunk applies one custom material to 785 buttons, so almost every visible node is "partial". We report it rather than loosen the definition.

You claim completeness. Complete with respect to what?

Per-snapshot capture and accounting — not state space.

We guarantee every node in a sampled frame is captured and every gap is recorded. We do not guarantee we reached every screen. We propose using the static template list as the denominator to measure that.

If static analysis can find all UI templates, why do you need a runtime sniffer at all?

Templates are not states.

Static analysis knows a shop-row template exists; it does not know there are seven rows, what they say, which is scrolled into view, or where animation left them. That concrete state only exists at runtime.

How does the auto-explorer work, and how do you know it explored enough?

Today it is a blind click script, and we do not know.

It clicks fixed positions per game and logs what it attempted. In the final measured runs it reached real screens — menus, settings, Spurpunk's map, and Unchained's in-game dialogue and pause menu — but it did not reach gameplay in Smoke Break, and it once got stuck on a splash screen. It has no coverage guarantee. A semantic explorer using the sniffer's own interactable list is the most important next step.

"208 distinct UI states" — couldn't a ticking timer or an animation inflate that?

Yes — heavily.

In Smoke Break, 202 of 208 fingerprints occur in exactly one snapshot: frames of the scrolling credits and button animations. Only 6 are held for half a second or more. Rounding positions to 2 px is not enough. We should count states by the set of visible templates, ignoring moving positions and changing numbers, and report that instead. The per-state coverage figures the method calls for are also not computed yet.

You compiled code into the game. That is not realistic for games you cannot rebuild.

Agreed; this requires cooperation from the developer.

The injected module is isolated in its own folder and assembly, and we verified it changes no original file. A deployment model would be an SDK the developer includes. Binary-only instrumentation is out of scope.

The mirror is passive. How would a player actually use offloaded UI?

They cannot yet — the input path is not built.

We established the output direction first. Routing a click on a mirrored button back to the matching game element (by node ID) is the next architectural piece.

Only 34% of Spurpunk's snapshots were displayed live. You are losing data.

Deliberately dropping stale frames, not losing data.

Snapshots are complete, so an old queued one carries nothing the newest does not. Without dropping them the mirror fell 5 seconds behind. Every snapshot is still recorded and replayed; the dropped count is reported.

Why is replay only 90.76% equivalent to live on Spurpunk?

Image arrival timing, and nothing structural.

Every mismatch is a frame where, live, an image had not arrived yet, while replay preloads all images. Geometry, hierarchy, visibility, order and clipping agreed on every comparable frame.

A mirror lag of about 150 ms is too slow for games.

For this prototype, yes; the cost is identified.

Most of it is parsing a 1.8 MB JSON document (about 62 ms on Unchained). A binary delta format removes most of that. The sniffer's own capture cost is 5–45 ms per sample, on a background-safe path.

Three student games, all Unity 2022.3. Does this generalise?

Not proven.

They do cover both Unity UI systems, a scriptable render pipeline and third-party UI extensions. Other engines, commercial games and custom UI frameworks are untested.

Fonts are never transported, so text never matches. Is that acceptable?

For measuring structure, yes; for a product, no.

We avoided copying licensed fonts. The string, size, colour and alignment are exact; glyph shapes and line wrapping are not. Options include rendering text to images on the source or shipping fonts the developer licenses for this.

What is the research contribution, as opposed to engineering?

A measured answer to "how much of a game's UI survives being sent as structure, and why the rest does not".

That includes a passive capture method, a way to separate capture, accounting and state completeness, and a taxonomy of fidelity loss backed by counts on real games. The offloading benefit itself — bandwidth, latency, accessibility — is not yet demonstrated.
